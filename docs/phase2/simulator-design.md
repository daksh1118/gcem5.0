# SLA Guardian — Phase 2 Simulator Design & Technical Specification
**Project:** SLA Guardian — Reinforcement Learning-Based Network Slicing and Resource Allocation for 5G  
**Phase:** Phase 2 — Network Simulator, Traffic Generator and Edge-Compute Model  
**Status:** Implemented, Tested, and Verified  
**Document Classification:** Fallback Discrete-Event Simulation Core (Abstracted 5G NR + MEC)  

---

## 1. Executive Summary & Design Scope

In Phase 0, an empirical audit established that ns-3 with 5G-LENA was not present on the Windows host and could not be provisioned within the 45-minute gate. Phase 2 delivers a **high-fidelity, deterministic discrete-event Python simulation core** (`FallbackNetworkSimulator`) designed to provide realistic cause-and-effect network slicing dynamics, packet queuing, and dual-stage resource allocation.

> **CRITICAL DISCLAIMER:**  
> All outputs, telemetry, and graphs generated by this component are **fallback discrete-event simulation outputs**. They are NOT physical-layer measurements from ns-3 or 5G-LENA. The simulator is designed as an abstracted 5G-inspired proxy to train RL policies, evaluate Safety Shield interventions, and benchmark resource-allocation controllers.

## 2. Architecture & Module Responsibilities

The simulator is located in `backend/app/simulator/` and consists of five decoupled modules:

```
backend/app/simulator/
├── __init__.py         # Package exports
├── queues.py           # Packet dataclass and PacketQueue FIFO management
├── traffic.py          # Seeded NumPy multi-slice Poisson/burst traffic generator
├── radio.py            # OFDMA bandwidth model with Rayleigh channel power fading
├── compute.py          # Multi-tenant edge-compute processing queue model
├── diagnostics.py      # Granular per-slice telemetry and KPI diagnostics
└── fallback.py         # Main FallbackNetworkSimulator implementing SimulatorInterface
```

### Component Breakdown
1. **`queues.py` (`Packet`, `PacketQueue`)**:
   Tracks packet-level metadata across its lifecycle: unique ID, slice ID, payload size (bytes), arrival time ($t_{\text{arrival}}$), deadlines, stage entry/exit times, and drop reasons.
2. **`traffic.py` (`TrafficGenerator`)**:
   Generates reproducible packet arrivals for `eMBB`, `URLLC`, and `mURLLC` slices driven by scenario configurations (`normal`, `urllc_burst`, `mixed_stress`).
3. **`radio.py` (`RadioModel`)**:
   Converts physical resource block (PRB) allocations into achievable physical transmission capacity, modulated by stochastic Rayleigh channel power gains.
4. **`compute.py` (`EdgeComputeModel`)**:
   Models edge cloud server CPU allocation, processing packets arriving from the radio stage. Demonstrates that edge compute bottlenecks can breach latency SLAs even with ample radio bandwidth.
5. **`diagnostics.py` (`StepDiagnostics`)**:
   Emits granular statistics (queue depths, offered packets, delivered packets, drops, p95 latency) and converts seamlessly to `SimulatorDiagnostics`.
6. **`fallback.py` (`FallbackNetworkSimulator`)**:
   Coordinates discrete-time progression, enforces resource invariants, updates `NetworkState`, and implements `SimulatorInterface`.

## 3. Unit System & Resource Accounting

To prevent dimensional ambiguity, every quantity in the simulator adheres to an explicit unit convention:

| Dimension | Physical Unit | Model Representation | Notes |
| :--- | :--- | :--- | :--- |
| **Radio Capacity** | Abstract Capacity Units / PRBs | `total_radio_capacity = 100.0` | $1.0\text{ unit} \equiv 1.0\text{ Mbps}$ baseline service rate |
| **Compute Capacity**| Abstract Compute Units / Cores | `total_compute_capacity = 100.0`| $1.0\text{ unit} \equiv 1.0\text{ Mbps}$ baseline compute service |
| **Packet Payload** | Bytes | $250 \dots 1400\text{ bytes}$ | eMBB: 1400 B, URLLC: 250 B, mURLLC: 500 B |
| **Throughput** | Megabits per second (Mbps) | $\text{Throughput} = \frac{\text{Bytes} \times 8}{10^6 \times \Delta t}$ | Measured over step interval |
| **Simulation Time**| Seconds (s) | `sim_time_sec` | Advanced by $\Delta t = 0.010\text{ s}$ ($10\text{ ms}$) per step |
| **Reported Latency**| Milliseconds (ms) | `p95_latency_ms` | End-to-end packet duration |
| **Queue Length** | Packets | `queue_depth_packets` | Radio queue + compute queue |
| **Channel Gain** | Dimensionless | $G_i \in [0.35, 1.85]$ | Rayleigh power fading ($E[G_i] \approx 1.0$) |

### Resource Invariants (Enforced at Every Step):
1. **Radio Conservation:** $\sum_{s} \text{radio\_allocation}[s] \le \text{total\_radio\_capacity} + \epsilon$.
2. **Compute Conservation:** $\sum_{s} \text{compute\_allocation}[s] \le \text{total\_compute\_capacity} + \epsilon$.
3. **Non-Negativity:** All allocations and queue depths are strictly $\ge 0$.
4. **Rejection of Invalid Actions:** If an unvalidated or out-of-budget `ExecutedAction` is passed to `step()`, the simulator raises a descriptive `ValueError` rather than silently clamping or adjusting it.

## 4. End-to-End Packet Lifecycle & Latency Definition

Every packet follows a deterministic two-stage pipeline:

```
[Arrival] 
   │ (t_arrival)
   ▼
[Radio Queue] ──(Radio Allocation * Service Rate * Channel Gain)──► [Radio Exit] 
                                                                          │ (t_radio_exit)
                                                                          ▼
[Delivered] ◄──(Compute Allocation * Compute Service Rate)──────── [Compute Queue]
   │ (t_compute_exit)
```

$$\text{End-to-End Latency (ms)} = (t_{\text{compute\_exit}} - t_{\text{arrival}}) \times 1000.0$$

$$\text{Radio Stage Delay (ms)} = (t_{\text{radio\_exit}} - t_{\text{radio\_enter}}) \times 1000.0$$

$$\text{Compute Stage Delay (ms)} = (t_{\text{compute\_exit}} - t_{\text{compute\_enter}}) \times 1000.0$$

### Drop Conditions:
- **Queue Overflow:** If queue size exceeds `max_packets = 5000`, new packets are dropped (`QUEUE_OVERFLOW_RADIO` or `QUEUE_OVERFLOW_COMPUTE`).
- **Deadline Expiration:** If a packet's age exceeds $1.5 \times \text{SLA Latency Threshold}$, it is purged from the queue as dropped (`DEADLINE_EXCEEDED_RADIO` or `DEADLINE_EXCEEDED_COMPUTE`).

## 5. Traffic Profiles & Scenarios

The generator models three distinct 3GPP workload classes:
1. **`eMBB` (Enhanced Mobile Broadband):**
   - High payload (1400 bytes), nominal $45\text{ Mbps}$.
   - Modulated with a slow sinusoidal wave ($T = 100\text{ steps}$) simulating user streaming sessions.
2. **`URLLC` (Ultra-Reliable Low-Latency Communication):**
   - Small payload (250 bytes), nominal $8\text{ Mbps}$, tight latency deadline ($7.5\text{ ms}$).
   - Periodic arrival with micro-bursts. In `urllc_burst` scenario, demand surges $4\times$ to $32\text{ Mbps}$.
3. **`mURLLC` (Massive / Mixed URLLC):**
   - Medium payload (500 bytes), nominal $15\text{ Mbps}$, latency deadline ($22.5\text{ ms}$).
   - High-density Poisson arrival process.

### Scenarios Supported:
- **`normal`:** Total offered load $\approx 68\text{ Mbps}$ (within $100\text{ Mbps}$ capacity). Minimal queuing.
- **`urllc_burst`:** URLLC demand jumps to $32\text{ Mbps}$ (total $\approx 92\text{ Mbps}$). Requires dynamic priority reallocation to protect URLLC SLA.
- **`mixed_stress`:** Overload condition (eMBB 80 Mbps, URLLC 25 Mbps, mURLLC 35 Mbps = $140\text{ Mbps}$). Triggers severe congestion and drops unless actively managed.

## 6. Edge-Compute Bottleneck Demonstration

A key architectural finding from Phase 0 was that radio slicing alone cannot guarantee SLAs if edge computing is saturated.

The test `backend/tests/test_simulator.py::test_compute_bottleneck_causes_latency_increase` proves this empirically:
- **Test Setup:** Allocate generous radio bandwidth ($30\text{ PRBs}$) to URLLC in both runs.
- **Run A (Balanced):** $30\text{ compute units}$ allocated $\to$ packets clear compute queue immediately; p95 latency remains low.
- **Run B (Bottlenecked):** $0.5\text{ compute units}$ allocated $\to$ packets successfully traverse the radio stage but accumulate in the compute queue, causing significant queuing delay and SLA violations.

## 7. Known Limitations Compared to Real ns-3 / 5G-LENA

| Aspect | Fallback Python Simulator | Real ns-3 / 5G-LENA |
| :--- | :--- | :--- |
| **Physical Layer (PHY)** | Abstract service rate with Rayleigh power envelope | Detailed 3GPP TS 38.211 numerologies, LDPC/Polar codes, CQI/MCS feedback, MIMO |
| **Medium Access (MAC)** | Discrete-time byte-budget queue draining | Symbol-by-symbol OFDMA slot scheduler, PDCCH/PDSCH/PUSCH grants, HARQ retransmissions |
| **Radio Propagation** | Bounded Rayleigh fading model | 3GPP TR 38.901 urban macro/micro, path loss, shadow fading, fast spatial fading |
| **Core Network** | Direct packet handoff to edge compute | NG-RAN to 5GC GTP-U tunnels, UPF routing, RRC signaling |
| **Edge Compute** | Explicit $M/M/c$ discrete-event queueing model | Not modeled natively in 5G-LENA (requires custom external coupling) |
| **Execution Speed** | $>1,000\text{ steps/second}$ in pure Python | $\sim 5\text{--}50\text{ steps/second}$ in compiled C++ discrete-event loop |
